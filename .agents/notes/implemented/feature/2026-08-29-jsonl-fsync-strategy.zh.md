# Agent Note: Configurable JSONL fsync strategy

Status: implemented

[English](2026-08-29-jsonl-fsync-strategy.md) | 中文

## 问题

JSONL 后端在每个追加批次 resolve 之前都执行 fsync。持久性最大，但流式会话为每个写入批次支付一次 fsync——token 流上一个回合可达数百次——在慢速磁盘上表现为 append 延迟。只需要"已完成的回合在崩溃后存活"的部署，没有办法把逐批次的同步代价换掉。

## 决策

后端接受 `sync` 配置，含两种策略：

- `'batch'`（默认）：每个追加批次在 append resolve 前 fsync——与今天的行为逐字节一致。
- `'turn'`：只有关闭 `turn/end` 边界的批次被 fsync——回合是日志的提交/重放边界，因此已完成的回合保持持久，而边界之间的批次依靠 OS 回写。崩溃可能丢失进行中回合的尾部，表现为撕裂尾部，并在下次打开时由既有的撕裂尾机制恢复；已完成的回合绝不回退。

两种策略下的回滚协议不变：写入或同步失败会把文件回滚到之前的长度，因为 coordinator 未改变的游标会重试该批次。

## 备选方案

**基于时间的 fsync（每 N 毫秒至多一次）。** 否决：崩溃可丢失的窗口不再由任何日志语义边界限定，且该旋钮会诱导盲目调优；回合边界是日志本就携带的有意义的提交线。

**逐事件 sync 而非逐批次。** 否决：比批次默认值严格更多的 fsync，却没有额外的持久性——批次本就是写入单元。

**按会话而非按后端的策略。** 否决：持久性是存储根的部署属性，不是单个会话的属性；一个后端一种策略，让格式与撕裂尾保证保持一致。

## 后果

`'turn'` 为高吞吐流去掉了每回合除一次之外的全部 fsync，代价是进行中回合内有界的崩溃窗口——由同一撕裂尾机制恢复，绝不损坏已提交前缀。默认 `'batch'` 行为不变，既有部署无需触碰配置即保持其持久性。

## 测试

`zstd.spec` 经 FileHandle `sync` spy 驱动两种策略：`'batch'` 下每个追加批次都 sync；`'turn'` 下无边界批次不做任何 sync、`turn/end` 批次恰好 sync 一次，且追加的事件完整加载回来。
