# Agent Note: Webhook ingress rate limiting and idempotent redelivery

Status: implemented

[English](2026-08-29-webhook-ingress-guard.md) | 中文

## 问题

GitHub 入口对每个请求都执行完整的受限 body 读取加 HMAC 验证——洪泛者想让接收方付出的成本恰好被全额满足，除 413 体积上限外没有任何速率约束。而重新交付的 `X-GitHub-Delivery` id 会重新调用每一条规则，因为 fire-and-forget 分发在任何规则运行之前就应答 202，GitHub 超时即重试。

## 决策

每个 handler 实例持有一个内存守卫，内含三种机制：

- 按源地址的令牌桶（`rateLimitCapacity` 突发、`rateLimitRefillPerSecond` 补充——插件配置，因为流量规模因部署而异），在任何 body 工作之前消耗：洪泛只付出廉价的 header 检查，得到 429。桶非空时 413 语义不变。
- 同一源地址连续十次签名失败会打开一个十秒熔断器，在进行任何 HMAC 或解析工作之前以 503 拒绝该源地址；一次验证成功即重置连击，冷却结束后下一次尝试从干净状态重新评估。边界为固定常量——那是滥用响应，而非流量策略。
- 每个 handler 记忆最近 1000 个已分发的 delivery id；已验证的重交付以 202 应答而不重新调用规则。id 只在分发被接受之后记录，因此分发失败的交付仍可重试；且只有通过验证的请求才能到达该检查——抑制一次真实交付需要共享密钥。

状态按 handler 实例保存在内存中，从不持久化。

## 备选方案

**以源地址 + delivery id 为键的令牌桶。** 否决：每次交付就是一个请求，按交付的令牌桶毫无意义；两个标识符各自拥有不同的机制——地址约束速率，delivery id 约束重复。

**把熔断边界做成插件配置。** 暂缓：阈值与冷却是滥用响应常量，而非部署可调的吞吐量；当某个部署确实需要不同姿态时再升级为配置。

**到达时记录实现去重。** 否决：分发抛出时会应答 503，而 GitHub 对非 2xx 重试——到达即记录会让重试得到 202，而规则从未运行，交付被静默丢弃。

## 后果

来自单一源的洪泛在突发耗尽后得到 429，且不再读取 body；签名猜测源每次被锁定十秒；GitHub 的超时重交付不再双重调用规则。守卫内存有界（见过的每个源地址一个桶——受实际观察到的源地址空间约束——加 1000 个 delivery id）。同一 id 的并发到达仍可能都分发（窗口按到达顺序），进程重启会遗忘窗口——新进程上 GitHub 的重交付会重跑规则，这是 fire-and-forget 分发既有的至多一次形态。

## 测试

`handler.spec` 经 HTTP 驱动真实 handler：三次请求的洪泛在突发耗尽后得到 429 且仅两次分发；重交付 id 应答一次 202；连续十次签名失败对有效签名打开熔断器，且成功会重置连击。`ingress.spec` 以注入时钟钉住守卫状态机：按时间流逝补充、容量上界、阈值与冷却转换、源地址独立性、幂等窗口驱逐。
